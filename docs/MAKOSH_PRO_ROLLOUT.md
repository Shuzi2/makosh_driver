# Makosh Pro: оновлення та повернення

Зелений дизайн Makosh Pro, анімації з підтримкою зменшення руху та розділ «Адмін панель»: користувачі, власний пароль, збережені місця та журнал дій. Адмінпанель доступна лише адміністраторам; інші ролі зберігають доступ до зміни власного пароля.

Поля та логіка рейсів, документи й ролі залишаються. Довідник місць — нова таблиця; у підказках нового рейсу показано активні адреси. Рейси зберігають власні рядки адрес, тому зміна чи архівація місця не змінює історію перевезень. Міграція 0002 лише створює таблицю.

## Перед запуском на сервері або ПК з Docker

Команди виконуються з папки проєкту. Перед оновленням перевірте `git status`: незакомічені локальні зміни потрібно зберегти окремо.

1. Збережіть `.env` у захищеному місці поза Git.
2. Виконайте `sh scripts/backup.sh`: це зупинить запис на час узгодженої резервної копії PostgreSQL та завантажень. Перевірте, що команда успішно завершилась; тримайте копію також поза сервером.
3. Оновіть код: `git pull --ff-only origin main`.
4. Застосуйте міграцію та перезберіть образ: `docker compose up -d --build web`.
5. Перевірте `docker compose ps`, вхід, адмінпанель, створення рейсу та документи. Міграція виконується сервісом `migrate`, від якого залежить `web`.

Оновлення GitHub саме по собі не оновлює Docker на ПК.

## Повернення попереднього вигляду й навігації

Перед оновленням у GitHub створено резервну гілку `backup/before-makosh-pro-2026-11-08` з попереднім `main` (`eae36723d568182a2d05e1c58ec9002741c9f5f4`).

Знайдіть коміт оновлення з повідомленням `Apply Makosh Pro and administration hub with saved places` та створіть зворотний коміт: `git revert <SHA_коміту_оновлення>`. Це повертає файли без переписування історії. Опублікуйте зворотний коміт у `main`, оновіть код на ПК та повторіть `docker compose up -d --build web`.

Для повернення коду не потрібно відновлювати стару БД. Не запускайте зворотну міграцію `fleet 0001`: вона видалить таблицю нових збережених місць. Залишена таблиця не заважає попередній версії; рейси, документи й нові записи залишаться в БД. Повне відновлення БД потрібне лише у випадку пошкодження даних, а не для скасування дизайну.
